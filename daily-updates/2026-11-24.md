## What we shipped today (both pushed to `main`)

Both are instances of the same lesson AGENTS.md already carries: **a field that
can hold `None`, or a unit that can round, is a place where a plausible-looking
answer is wrong.**

### `tiny-log` 0.8.3 — `bytes_human` chose the unit before it rounded

`bytes_human(1023.9999)` returned **`"1024.0 B"`** — 1024 bytes labelled with
the byte unit. The unit was picked before the value was rounded, so any value
within a rounding step of a boundary printed a number equal to the next unit's
base while carrying this unit's label. A caller that strips the suffix and
parses the number gets a **1024x error**, which is exactly what a dashboard does
with a telemetry field.

| input | 0.8.2 | 0.8.3 |
|---|---|---|
| `bytes_human(1023.9999)` | `1024.0 B` | `1 KB` |
| `bytes_human(1048575.99)` | `1024.0 KB` | `1 MB` |
| `bytes_human(1023.6, precision=0)` | `1023 B` | `1 KB` |
| `bytes_human(float("inf"))` | `OverflowError` | `inf B` |

Also: `precision=0` **truncated** via `int(v)` where `f"{v:.0f}"` rounds — an
explicit precision of zero is still a rounding request. And `inf` reached
`int(value)` unguarded: the function had a NaN guard, and infinity is the other
non-finite float. A field formatter must never raise inside a logging call.
Third fix in the same file: `SamplingHandler(rates={logging.DEBUG: 0.0})` stored
the key `"10"` and looked up `"DEBUG"`, so the rate read back as the default
`1.0` and **every DEBUG record was kept**. 13 new tests; 8 red on 0.8.2;
140 passed.

### `tiny-validator` 0.7.4 — `nullable` was the missing half of "optional"

The library could say a key may be **absent** (`required=False`) but not that it
may be **present and `null`**. `Field.allow_none` was a read-only class property
that only `Any` overrode; `fields.String(allow_none=True)` raised `TypeError`.
The only spelling a user could reach for was

```python
fields.String(required=False, default=None)
```

and that produced a schema which **rejected every document** — the `None`
default is validated as a value *before* the field is allowed to be absent:

```
validate({}) -> [{'path': 'tags', 'message': 'value is null'}]
```

`Field` now takes `nullable=True/False`, independent of `required`; a `None`
default implies nullable. Mirror defect in the JSON Schema bridge:
`from_json_schema` accepted `{"type": ["string", "null"]}` by **stripping
`"null"`** and building a non-nullable field, so a contract imported from
OpenAPI/MCP rejected the nulls it explicitly permitted. `"nullable": true`
raised as an unsupported keyword. Both forms now import, and the exporter emits
`"nullable": true` so it no longer advertises a narrower contract than the
validator enforces. 14 new tests; 11 red on 0.7.3; 234 passed.

## Signal for the roadmap

Both of today's defects were **documents that validated when they should
have failed, and vice versa**: a unit label that contradicts its own number,
and a schema that rejects the shape it describes. They are the same class as
the `"optional dependency"` issue stream above — the failure surfaced somewhere
unhelpful. The next `tiny-*` audit should grep for **agreement between two
things that are computed separately** (value vs. unit, required vs. nullable,
export vs. import) rather than for a named bug pattern.
