## Actionable insight for our projects

**Our `tiny-mcp-client` is missing exactly the feature the ecosystem is asking for, and the ask is unanswered.**

| what rugsnare does | our tiny-mcp-client today |
|---|---|
| sha-256 contract digest over tool name/description/inputSchema | **no digest, no snapshot, no contract concept at all** |
| diffs two published server versions | **no version diffing** |
| outputSchema hashed separately from inputSchema | **not modelled** |
| open source, zero dependencies | zero-dep Python ✅ (this is the differentiator) |

Our client already exposes `list_tools()` / `list_resources()` / `list_prompts()` — the exact three calls a contract snapshot needs. The gap is the *snapshot and diff* layer on top, not the client.

**Why this is the highest-leverage thing we can ship:** the demand is public, quantified and unanswered. Issue #5414 has **0 maintainer replies after 6 days**, and the fix is explicitly scoped as "a 10-line CI gate" inside a repo we already mirror the structure of. A zero-dependency Python implementation of contract snapshot + diff + a CI gate is a direct, auditable answer to a numbered, open issue in the canonical MCP repo — the best discovery channel available to us, and it is *far* better than the PyPI situation below.

**Concrete plan (one package, ~300 lines, zero deps):**
1. `tiny-mcp-contract` — `snapshot(client) -> ContractSnapshot`, `diff(a, b) -> list[Change]`, `digest(snapshot) -> sha256`. Change kinds: BREAKING / NEW / GONE / NOTATION / RELAXED — the exact taxonomy in #5414.
2. Classify BREAKING as a **release blocker**: same fail-closed rule we already applied to `tiny-headers-redact`.
3. Ship a CI gate that diffs the contract against the previous published version and fails on BREAKING, with the diff in the PR body — literally what the issue asks for.
4. Open the PR to `modelcontextprotocol/servers` as a 10-line gate, and cross-post the Python implementation to rugsnare's issue thread as a second implementation.

**Second, still true and still cheap: the distribution gap.** `tiny-mcp-client`, `tiny-mcp-server`, `tiny-mcp-registry` all **404 on PyPI**, and **31 of our Python repos have no release workflow** (only `tiny-sandbox` and `snapdb` do). The contract package must ship with a release workflow from day one or it repeats the same pattern.

**Third rule (new, from today): a repo's open-issue count is a maturity signal, not just noise.** `t3code` has **4,711 open issues** on 44,706 stars and `rea` has **1,718** on 427,642. Both are moving fast with a large unresolved backlog — that is where contributors can still land a fix the maintainers want, which is exactly the `Go-Hybrid` model. A repo with 100 open issues is crowded; a repo with 4,711 and no triage is an invitation.
