## Actionable insight for our projects

**Our `tiny-mcp-client` is missing exactly the feature the ecosystem is asking for, and the ask is unanswered.**

| what rugsnare does | our tiny-mcp-client today |
|---|---|
| sha-256 contract digest over tool name/description/inputSchema | **no digest, no snapshot, no contract concept at all** |
| diffs two published server versions | **no version diffing** |
| outputSchema hashed separately from inputSchema | **not modelled** |
| open source, zero dependencies | zero-dep Python ✅ (this is the differentiator) |

Our client already exposes `list_tools()` / `list_resources()` / `list_prompts()` — the exact three calls a contract snapshot needs. The gap is the *snapshot and diff* layer on top, not the client.

**Why this is the highest-leverage thing we can ship:** the demand is public, quantified and unanswered. Issue #5414 has **0 maintainer replies after 6 days**, and the fix is explicitly scoped as "a 10-line CI gate" inside a repo we already mirror the structure of. A zero-dependency Python implementation of contract snapshot + diff + a CI gate is a direct, auditable answer to a numbered, open issue in the canonical MCP repo — the best discovery channel available to us, and it is *far* better than the PyPI situation below.

**Concrete plan (one package, ~300 lines, zero deps):**
1. `tiny-mcp-contract` — `snapshot(client) -> ContractSnapshot`, `diff(a, b) -> list[Change]`, `digest(snapshot) -> sha256`. Change kinds: BREAKING / NEW / GONE / NOTATION / RELAXED — the exact taxonomy in #5414.
2. Classify BREAKING as a **release blocker**: same fail-closed rule we already applied to `tiny-headers-redact`.
3. Ship a CI gate that diffs the contract against the previous published version and fails on BREAKING, with the diff in the PR body — literally what the issue asks for.
4. Open the PR to `modelcontextprotocol/servers` as a 10-line gate, and cross-post the Python implementation to rugsnare's issue thread as a second implementation.

**Second, still true and still cheap: the distribution gap.** `tiny-mcp-client`, `tiny-mcp-server`, `tiny-mcp-registry` all **404 on PyPI**, and **31 of our Python repos have no release workflow** (only `tiny-sandbox` and `snapdb` do). The contract package must ship with a release workflow from day one or it repeats the same pattern.

**Third rule (new, from today): a repo's open-issue count is a maturity signal, not just noise.** `t3code` has **4,711 open issues** on 44,706 stars and `rea` has **1,718** on 427,642. Both are moving fast with a large unresolved backlog — that is where contributors can still land a fix the maintainers want, which is exactly the `Go-Hybrid` model. ## The `tiny-worktree` repo

**Why it exists.** Plain `git worktree` asks you to type the branch name
twice and the path once, and the two have to agree. Six agents working one
repo overnight is six chances to get that wrong. `tiny-worktree` takes the
branch name and derives everything else, so the same repo + same branch
always resolves to the same path.

**What shipped.**

- 38 tests, all against **real throwaway git repositories** — a mocked git
  would only test the mock.
- Python 3.8, 3.9, 3.10, 3.11, 3.12, all green.
- Zero runtime dependencies.
- A CI `build` job that **asserts the wheel actually contains the module**,
  not just that the build succeeded.

**Three real bugs the test suite caught while building it:**

1. **`git worktree add` takes the path BEFORE the commit-ish.** The other
   order fails with `fatal: not a valid object name: <path>` — which reads
   like a path problem but is an argument-order problem.
2. **`prune(dry_run=True)` must pass git's `-n`.** `--verbose` alone
   still prunes, so a caller who believed they were previewing would have
   silently deleted the stale administrative entries.
3. **`py-modules = ["tiny_worktree"]` on a package DIRECTORY builds a
   wheel that ships nothing.** The build succeeds; the install imports
   nothing. This is the same defect class that shipped in `tiny-router` and
   `tiny-validator` earlier this year, and it is now guarded by a test
   that parses `pyproject.toml` and a CI job that inspects the wheel.

The first three guards were each **proven to fail** against the unfixed
code before the fix was accepted.

**Measured, not asserted:**

| operation | time |
|---|---:|
| raw `git worktree add` + remove | 12.6 ms |
| `tiny-worktree` new + remove | 17.5 ms |
| `list_worktrees()` | 3.5 ms |

The overhead is the Python-side path computation and error handling, and it
is the same order as the git calls themselves. For setting up one worktree
before a long agent task, that is not the bottleneck.

## What the PyPI numbers actually mean

Yesterday's report said: *"We have a distribution gap, not a quality gap —
and it is measurable."* Today's numbers put a ratio on it.

`cachetools` does 233 million downloads a month. `fast-cache` does 0,
because it is not on PyPI. `python-dotenv` does 582 million. `tiny-config`
does 0, for the same reason.

And the numbers that *look* like ours are not. Of the 45 Python packages
in `repos/`, exactly one — `pysnapdb` — is published under a name we
own. It does 13 downloads a month. Four more of our names are taken by
other developers, so their download counts belong to someone else.

This is not a quality signal. `fast-cache` benchmarks at 2.2M ops/sec;
`cachetools` does not claim to be faster than a dict. The gap is that
**`pip install fast-cache` fails**, so nobody ever gets to the benchmark.
The whole point of the zero-dependency movement is that the first thing a
developer does is `pip install`, and for 40 of our 45 Python packages that
first step fails with `No matching distribution found`.

The blocker is not a code problem and it is not a secrets problem. It is
that the PyPI token lives **only** in GitHub Actions (the `pypi` environment
on `snapdb`) and there is no local credential to publish with, and no
publish workflow on any of the other 44 packages.

**The fix is a workflow, not a token.** One `release.yml` per repo that
builds, verifies the wheel contents, and publishes on a tag — pointed at
the same `pypi` environment that already works for `snapdb`. That is a
day of work and it converts 40 zeros into real numbers.

**But first, the names.** Four of our package names are already taken on
PyPI by other developers, so publishing under them is not an option. Each
needs a distinct name, and each new name has to be checked against PyPI
*before* it goes into a `pyproject.toml` — never assumed free just because
it is free on GitHub. A 404 from `https://pypi.org/pypi/<name>/json` means
the name is free; anything else means it is not.
