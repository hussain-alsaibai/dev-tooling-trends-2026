## The signal: "silently dropped" is a named, recurring defect class

Three bounded `is:issue is:open` searches:

| query | open issues |
|---|---|
| `"was silently dropped"` | **1,913** |
| `"was silently dropped" created:>2026-11-11` | **178** |
| `"silently ignored" created:>2026-11-01` | 3,438 |
| `"partial update"` | 23,795 |

1913 issues describe a value that was dropped without an error, and 178 of
those were opened in the last 15 days — roughly **12 a day**. This is not a
legacy wart; it is a defect class that keeps being written.

The naming is the interesting part. A bug titled *"field X is wrong"* is a bug.
A bug titled *"field X was silently dropped"* is a **reliability** failure: the
caller had no signal, and the system's state now disagrees with what the caller
believes it wrote. Every such issue is a place where a test suite was green and
a data set was incomplete.

Today's `snapdb` fix is one instance of it. The generalisation worth carrying:

- **A write API's name is a contract.** `update` means "change what I named",
  not "make this the record". `replace`/`put`/`set` mean the second thing.
  When one function is spelled like the first and behaves like the second, the
  caller's correct mental model becomes the bug.
- **The dangerous payload is the partial one.** 264 `snapdb` tests were green
  and every one of them passed a complete record to `update`. A rewrite and a
  patch are indistinguishable when the payload is complete, so the suite
  proved only the spelling that cannot fail.
- **Silence is the defect, not the `IndexError`.** Updating a row that does not
  exist used to write a placeholder row — no error, a new row. The fix raises.
  A write that has nowhere to go should say so.

## What we shipped today (same day as this report)

- **`tiny-validator` 0.7.5** — `from_json_schema` enforced `enum` but never
  recorded it, so an imported enum disappeared on re-export. The Schema kept
  rejecting bad values; the *published contract* no longer did. Consumers of
  the exported document (OpenAPI, MCP tool schemas, generated clients)
  accepted every string. 12 tests, 6 red on 0.7.4.
- **`snapdb` 0.18.5** — `DocumentStore.update()` was a whole-record write with
  patch syntax (above). 13 tests, 10 red on 0.18.4.

Both are the same shape, from opposite sides: **the artifact the other system
reads disagreed with the rule this system enforced.** For the validator, the
export outlived the constraint; for the store, the caller's intent outlived the
payload. In both cases every validation-only test was green.

## For our projects

1. `snapdb` PyPI (`pysnapdb`): **16 downloads last month** (24 on 11-24, 76 on
   11-19, 716 before that). The trend is still down and still not a feature
   problem. The README install line resolves; the package has no audience. A
   feature release does not move this number — a post in a place where people
   choose an embedded store for agent state would.
2. Stop treating a green suite as evidence about a write path. Add one test per
   write API that passes the **minimum** valid payload, because that is the
   payload that distinguishes a patch from a rewrite.
3. `snapdb` known limitation, now documented in CHANGELOG: a real `0` in an
   int/float field on a nullable column reads back as absent — the empty slot
   and zero share bytes. Fixing it needs a per-column presence sentinel and a
   row-width change; it is the same "cannot distinguish absent from zero"
   family that v0.18.4 addressed for strings, one type over.
