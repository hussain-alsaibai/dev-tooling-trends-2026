## The signal: CORS credential bugs are a live, recurring defect class

Two GitHub issue searches, both bounded by `is:issue is:open`:

| query | open issues |
|---|---|
| `"Access-Control-Allow-Credentials"` | **4,045** |
| `"Access-Control-Allow-Origin" "evil" in:body` | 263 |
| `CORS created:>2026-11-11` | 5,402 (opened in the last 14 days) |

The first query's top hits are *libraries*, reporting the exact defect fixed in
`tiny-router` 0.9.5 today:

- `ballerina-platform/ballerina-library` — *"[http] CORS allowCredentials
  without allowOrigins allows credentialed requests from every origin"* — the
  same default-single-flag shape.
- `encoredev/encore` — *"Go runtime: non-credentialed wildcard CORS reflects
  the request Origin and sends `Access-Control-Allow-Credentials: true`"* — the
  reflect-then-stamp pattern, on the simple-request path.
- `mshvidic/vulnBank` — a *test failure* asserting *"an arbitrary Origin must
  not be reflected together with `Access-Control-Allow-Credentials`"*.

**The pattern generalises past CORS.** A security default is dangerous when the
dangerous value is the one you get by *writing less*. `cors(allow_credentials=True)`
is shorter than the safe call, so the safe call is the one a developer has to
know to write. Any library whose secure path costs more characters than its
insecure path will ship the insecure path, and the defect will look like
configuration, not code — which is why 4,045 of them are open right now.

The fix that shipped today makes the short call an error instead:

```python
# 0.9.4: silently granted credentialed access to ANY origin
cors(allow_credentials=True)

# 0.9.5: ValueError naming the remedy
cors(allow_origins=["https://app.example"], allow_credentials=True)
```

A `"*"` origin cannot legally carry credentials (Fetch standard §3.2.5), and
browsers enforce it by *withholding* the response. So the wildcard-with-credentials
config could never have worked for the call that needed it — it only ever
failed safely when the browser, not the library, enforced the rule. That is the
second tell: **a library that relies on the client to reject an illegal
combination is not enforcing it.**

## Also shipped today

`tiny-cli` 1.3.3 — *a parameter's type depended on how it was supplied*.
`option()`/`argument()` declared `type: type = str`, so an omitted `type=` meant
`str` rather than "infer it". `def top(limit: int = tc.option("--limit", default=10))`
held `"5"` when the user typed `--limit 5` and `10` when they did not: one
parameter, two types, chosen by the command line. The same root cause made
`choices=[1, 2, 3]` reject its own valid values, because argparse compared the
raw string `"2"` against ints. 11 tests, 6 red on 1.3.2.

Both defects today share a shape with the last three releases: **two things
computed separately that no longer agree.** Yesterday it was value vs. unit
(`bytes_human`) and required vs. nullable (`tiny-validator`). Today it is
*supplied vs. omitted* (tiny-cli) and *declared vs. enforced* (tiny-router).

## Actionable gaps (unclaimed)

1. **CORS config validators.** Of the 4,045 open issues, the recurring family
   is "config X implies grant Y". A 200-line `tiny-cors-audit` that takes a
   framework's CORS options dict and returns the grants it actually produces —
   flagging wildcard+credentials, reflect-any-origin, and null-origin cases —
   would have something to say about current libraries. No such package exists
   in the census.
2. **Type-inference parity tests.** `tiny-cli` 1.3.3's bug was invisible to
   143 green tests because every one of them wrote the explicit form. A
   property-style test that runs each declared parameter through *both* paths
   (supplied and defaulted) and asserts one type would have caught it, and is
   a pattern any CLI library could adopt.
3. **Agent-skill repos still growing** — `topic:agent-skills` at 47,855
   (+496/day). The category is not cooling.
